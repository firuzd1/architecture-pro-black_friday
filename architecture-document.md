# Архитектурный документ: MongoDB шардирование, репликация и миграция на Cassandra

## Задание 7. Проектирование схем коллекций для шардирования

### Коллекция `orders`

```json
{
  "_id": ObjectId(),
  "order_id": "ORD-123456",
  "user_id": "USR-789",
  "created_at": ISODate("2024-11-29T10:00:00Z"),
  "items": [
    { "product_id": "PROD-001", "name": "Смартфон X", "price": 49999, "quantity": 1 },
    { "product_id": "PROD-002", "name": "Чехол", "price": 999, "quantity": 2 }
  ],
  "status": "delivered",
  "total_amount": 51997,
  "geo_zone": "RU-MSK"
}
```

**Анализ операций:**
- Создание заказов — частые записи в пиковые периоды
- Поиск истории заказов конкретного пользователя — `{ user_id: "..." }`
- Отображение статуса заказа — `{ order_id: "..." }`

**Кандидаты на шард-ключ:** `user_id`, `geo_zone`, `{ user_id, created_at }`

**Выбранная стратегия:** хешированное шардирование по `user_id`

```javascript
sh.shardCollection("somedb.orders", { "user_id": "hashed" })
```

**Обоснование:** Большинство запросов идут по `user_id` — история заказов, текущий статус. Хеширование обеспечивает равномерное распределение данных по шардам даже в пиковые периоды (чёрная пятница), когда одновременно создаются тысячи заказов от разных пользователей. `geo_zone` не подходит, потому что часть зон будет значительно горячее других. Составной ключ `{ user_id, created_at }` усложнил бы балансировку без видимых преимуществ.

### Коллекция `products`

```json
{
  "_id": ObjectId(),
  "product_id": "PROD-001",
  "name": "Смартфон X",
  "category": "electronics",
  "price": 49999,
  "stock": {
    "RU-MSK": 50,
    "RU-EKB": 30,
    "RU-KLN": 20
  },
  "attributes": {
    "color": "black",
    "storage": "128GB"
  }
}
```

**Анализ операций:**
- Частые обновления остатков при каждой покупке
- Поиск по категории с фильтрацией по цене — `{ category: "electronics", price: { $gte: 10000 } }`
- Просмотр страницы товара — `{ product_id: "..." }`

**Кандидаты на шард-ключ:** `category`, `product_id`

**Выбранная стратегия:** хешированное шардирование по `product_id`

```javascript
sh.shardCollection("somedb.products", { "product_id": "hashed" })
```

**Обоснование:** Шардирование по `category` создаст горячий шард для категории «Электроника», так как 70% запросов приходится именно на неё — именно такая ситуация уже произошла и привела к сбою. Хешированный `product_id` распределяет товары равномерно вне зависимости от популярности категории. Запросы по категории будут идти на все шарды через scatter-gather, что немного медленнее, но это приемлемо для операций чтения каталога.

### Коллекция `carts`

```json
{
  "_id": ObjectId(),
  "user_id": "USR-789",
  "session_id": "SESS-abc123",
  "items": [
    { "product_id": "PROD-001", "quantity": 1 },
    { "product_id": "PROD-005", "quantity": 3 }
  ],
  "status": "active",
  "created_at": ISODate("2024-11-29T09:45:00Z"),
  "updated_at": ISODate("2024-11-29T09:55:00Z"),
  "expires_at": ISODate("2024-11-30T09:45:00Z")
}
```

**Анализ операций:**
- Получение корзины по `{ session_id, status: "active" }` для гостей
- Получение корзины по `{ user_id, status: "active" }` для авторизованных
- Слияние гостевой корзины в пользовательскую при логине
- TTL-удаление через `expires_at`

**Кандидаты на шард-ключ:** `user_id`, `session_id`

**Выбранная стратегия:** хешированное шардирование по `user_id`

```javascript
sh.shardCollection("somedb.carts", { "user_id": "hashed" })
```

**Обоснование:** Основные операции с корзиной идут по `user_id`. При слиянии гостевой корзины в пользовательскую обе корзины находятся рядом, если шардировать по `user_id`. Гостевые корзины (с `session_id` вместо `user_id`) можно хранить с `user_id: null` — они попадут на один шард, что некритично, так как гостевые корзины живут недолго и удаляются по TTL.

Индексы для поддержки операций:
```javascript
db.carts.createIndex({ "session_id": 1, "status": 1 })
db.carts.createIndex({ "user_id": 1, "status": 1 })
db.carts.createIndex({ "expires_at": 1 }, { expireAfterSeconds: 0 })
```

## Задание 8. Выявление и устранение «горячих» шардов

### Метрики мониторинга

**1. Распределение данных и чанков**

Основная метрика — количество чанков и документов на каждом шарде. Дисбаланс виден сразу:

```javascript
// Статистика по шардам
db.helloDoc.getShardDistribution()

// Детальная информация о чанках
use config
db.chunks.aggregate([
  { $group: { _id: "$shard", count: { $sum: 1 } } },
  { $sort: { count: -1 } }
])
```

**2. Нагрузка на операции**

```javascript
// Статистика операций на каждом шарде
db.serverStatus().opcounters

// Топ медленных запросов
db.system.profile.find().sort({ millis: -1 }).limit(10)
```

**3. Использование ресурсов**

Метрики которые нужно собирать:
- `opcounters.insert`, `opcounters.query`, `opcounters.update` — количество операций в секунду
- `wiredTiger.cache.bytes currently in the cache` — использование кеша
- `connections.current` — текущие подключения
- Задержка репликации на secondary нодах

```javascript
// Проверка задержки репликации
rs.printSecondaryReplicationInfo()

// Состояние replica set
rs.status()
```

**4. Признаки горячего шарда**

Шард считается горячим если:
- На него приходится более 30% всех операций при равном числе чанков
- Время ответа на запросы в 2+ раза выше среднего по кластеру
- Использование CPU стабильно выше 70%

### Механизмы перераспределения данных

**Автоматический балансировщик MongoDB**

MongoDB запускает балансировщик автоматически, но его можно настроить:

```javascript
// Проверить статус балансировщика
sh.getBalancerState()

// Включить балансировщик
sh.startBalancer()

// Настроить окно для балансировки (например, ночью)
use config
db.settings.updateOne(
  { _id: "balancer" },
  { $set: { activeWindow: { start: "02:00", stop: "06:00" } } },
  { upsert: true }
)
```

**Ручное перераспределение чанков**

Если автоматический балансировщик не справляется, можно переместить чанки вручную:

```javascript
// Посмотреть чанки на горячем шарде
use config
db.chunks.find({ shard: "shard1" }).limit(5)

// Переместить конкретный чанк на другой шард
sh.moveChunk(
  "somedb.products",
  { product_id: <значение из границы чанка> },
  "shard2"
)
```

**Решение проблемы с категорией «Электроника»**

Конкретно для ситуации из задания — 70% запросов на электронику — нужно:

1. Убедиться что шард-ключ не `category` (если он таковым является, придётся менять стратегию)
2. Если шардирование по `product_id` с хешированием уже настроено, проблема решается сама — товары из электроники распределены по всем шардам равномерно
3. Добавить индекс для ускорения запросов по категории:

```javascript
db.products.createIndex({ "category": 1, "price": 1 })
```

**Настройка размера чанков**

При высокой нагрузке уменьшение размера чанков помогает балансировщику быстрее перераспределять данные:

```javascript
use config
db.settings.updateOne(
  { _id: "chunksize" },
  { $set: { value: 32 } },  // уменьшить с 64MB до 32MB
  { upsert: true }
)
```

## Задание 9. Настройка чтения с реплик и консистентность

### Таблица операций чтения

| Коллекция | Операция | Куда читать | Обоснование |
|-----------|----------|-------------|-------------|
| **orders** | Создание заказа (запись) | Primary | Запись всегда на primary |
| **orders** | Отображение статуса заказа пользователю | Primary | Пользователь только что оформил заказ и ожидает актуальный статус. Устаревший статус вызовет панику |
| **orders** | История заказов пользователя | Secondary | Исторические данные не меняются часто, небольшая задержка некритична |
| **orders** | Аналитика и отчёты | Secondary | Аналитические запросы не требуют свежих данных, зато снимают нагрузку с primary |
| **products** | Страница товара (описание, цена) | Secondary | Описание и цена меняются редко, задержка в несколько секунд незаметна |
| **products** | Остаток товара при добавлении в корзину | Primary | Критично — нельзя продать товар которого нет. Чтение с secondary может показать устаревший остаток |
| **products** | Остаток при оформлении заказа | Primary | Финальная проверка перед списанием — только primary |
| **products** | Каталог и поиск по категориям | Secondary | Пользователь просматривает каталог, небольшая задержка незаметна |
| **carts** | Получение текущей корзины | Primary | Корзина активно меняется — пользователь добавляет и удаляет товары. Устаревшие данные приведут к потере изменений |
| **carts** | Слияние гостевой корзины | Primary | Операция требует точных актуальных данных обеих корзин |
| **carts** | Статистика брошенных корзин | Secondary | Аналитика, данные не критичны к свежести |

### Настройка Read Preference в приложении

```python
# Чтение с secondary для истории заказов
from pymongo import MongoClient, ReadPreference

client = MongoClient("mongodb://mongos_router:27020")
db = client.somedb

# Для некритичных операций — secondary
orders_secondary = db.get_collection(
    "orders",
    read_preference=ReadPreference.SECONDARY_PREFERRED
)

# Для критичных операций — primary
orders_primary = db.get_collection(
    "orders",
    read_preference=ReadPreference.PRIMARY
)
```

### Допустимая задержка репликации

| Коллекция | Допустимая задержка | Комментарий |
|-----------|--------------------|-|
| **orders** (статус) | 0 — только primary | Пользователь видит статус сразу после оформления |
| **orders** (история) | до 30 секунд | История не меняется, небольшая задержка некритична |
| **products** (остатки) | 0 — только primary | Риск продажи недоступного товара |
| **products** (каталог) | до 60 секунд | Обновление каталога не происходит мгновенно в любом случае |
| **carts** | 0 — только primary | Корзина меняется постоянно и быстро |

Мониторинг задержки репликации:

```javascript
// Проверить отставание secondary
rs.printSecondaryReplicationInfo()

// Установить алерт если задержка больше 10 секунд
// (настраивается в системе мониторинга, например Prometheus + MongoDB Exporter)
```

## Задание 10. Миграция на Cassandra

### 10.1 Какие данные переносим и почему

**Переносим в Cassandra:**

**Корзины (`carts`)** — идеальный кандидат. Огромное количество одновременных операций записи в пиковые моменты (добавление товара, обновление количества). Данные живут недолго (TTL), геораспределённость полезна — пользователь из Екатеринбурга должен получать корзину быстро. Строгая консистентность не нужна — если корзина чуть устарела на 100мс, это незаметно.

**Пользовательские сессии** — высокая частота чтения и записи, короткое время жизни, нет сложных связей между данными. Cassandra с TTL справляется с этим лучше MongoDB.

**История заказов (для чтения)** — после создания заказ практически не меняется. Нужно быстро читать историю конкретного пользователя. Cassandra отлично подходит для паттерна "много записей, чтение по одному ключу".

**Оставляем в MongoDB:**

**Активные заказы (`orders`)** — требуют транзакций при создании (списание остатков + создание заказа). Cassandra не поддерживает многострочные транзакции, это критично для целостности данных магазина.

**Товары (`products`)** — сложные запросы с фильтрацией по категории, цене, атрибутам. MongoDB с индексами справляется лучше. К тому же остатки нужно обновлять атомарно вместе с созданием заказа.

### 10.2 Модель данных в Cassandra

**Таблица `carts`**

```cql
CREATE TABLE carts (
    user_id     TEXT,
    session_id  TEXT,
    status      TEXT,
    product_id  TEXT,
    quantity    INT,
    updated_at  TIMESTAMP,
    expires_at  TIMESTAMP,
    PRIMARY KEY ((user_id), status, updated_at)
) WITH CLUSTERING ORDER BY (status ASC, updated_at DESC)
  AND default_time_to_live = 86400;
```

Partition key: `user_id` — все данные одного пользователя на одной партиции, запрос корзины = один узел.

Clustering key: `status, updated_at` — сортировка позволяет быстро находить активную корзину (`status = 'active'`) и последнюю версию.

Для гостевых корзин отдельная таблица:

```cql
CREATE TABLE guest_carts (
    session_id  TEXT,
    product_id  TEXT,
    quantity    INT,
    updated_at  TIMESTAMP,
    expires_at  TIMESTAMP,
    PRIMARY KEY ((session_id), updated_at)
) WITH CLUSTERING ORDER BY (updated_at DESC)
  AND default_time_to_live = 3600;
```

**Таблица `order_history`**

```cql
CREATE TABLE order_history (
    user_id     TEXT,
    created_at  TIMESTAMP,
    order_id    TEXT,
    items       LIST<FROZEN<MAP<TEXT, TEXT>>>,
    status      TEXT,
    total       DECIMAL,
    geo_zone    TEXT,
    PRIMARY KEY ((user_id), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC);
```

Partition key: `user_id` — запрос истории заказов пользователя попадает на одну партицию.

Clustering key: `created_at DESC` — последние заказы всегда первые, пагинация работает эффективно.

**Таблица `user_sessions`**

```cql
CREATE TABLE user_sessions (
    session_id  TEXT,
    user_id     TEXT,
    created_at  TIMESTAMP,
    last_seen   TIMESTAMP,
    data        MAP<TEXT, TEXT>,
    PRIMARY KEY ((session_id))
) WITH default_time_to_live = 7200;
```

**Обоснование по горячим партициям:**

В MongoDB проблема была в том, что `category = 'electronics'` концентрировала 70% запросов на одном шарде. В Cassandra мы шардируем по `user_id` — даже если 70% пользователей смотрят электронику, их запросы распределены по всем узлам кластера, потому что у каждого пользователя свой `user_id` и своя партиция.

При добавлении новых узлов Cassandra использует consistent hashing — данные перемещаются только с соседних узлов, а не перераспределяются полностью как в MongoDB. Это решает проблему с latency при масштабировании во время пиковой нагрузки.

### 10.3 Стратегии восстановления целостности данных

**Hinted Handoff**

Когда узел временно недоступен, координатор сохраняет запись у себя и отправляет её на целевой узел когда тот восстановится.

Применяем для: `carts` и `user_sessions`. Эти данные часто пишутся и не критичны к строгой консистентности. Если узел упал на несколько минут, корзина восстановится автоматически без потерь. Latency запросов при этом не страдает.

```cql
-- При создании keyspace для корзин
CREATE KEYSPACE shop_carts
WITH replication = {
    'class': 'NetworkTopologyStrategy',
    'RU': 3,
    'EU': 2
}
AND durable_writes = true;
```

Запись с `CONSISTENCY LOCAL_QUORUM` — достаточно подтверждения от большинства узлов в локальном датацентре, Hinted Handoff доставит остальным.

**Read Repair**

При чтении Cassandra сравнивает данные с нескольких реплик и исправляет устаревшие. Происходит автоматически, иногда асинхронно.

Применяем для: `order_history`. Заказы читаются часто (пользователи проверяют историю), пишутся редко (только при создании). Read Repair гарантирует что реплики синхронизируются при каждом чтении без дополнительных затрат. Уровень консистентности:

```cql
-- Чтение истории заказов
SELECT * FROM order_history
WHERE user_id = 'USR-789'
LIMIT 20;
-- с CONSISTENCY QUORUM
```

**Anti-Entropy Repair**

Фоновый процесс который сравнивает данные между репликами через Merkle trees и синхронизирует расхождения. Запускается вручную или по расписанию.

Применяем для: всех таблиц как фоновая профилактика, но особенно важно для `order_history` — заказы нельзя терять даже если реплика долго была недоступна.

```bash
# Запуск repair для keyspace истории заказов
nodetool repair shop_orders

# Инкрементальный repair (только изменения с последнего запуска)
nodetool repair --incremental shop_orders

# Запуск по расписанию — раз в неделю в нерабочее время
# Добавить в crontab:
# 0 3 * * 0 nodetool repair shop_orders
```

**Итоговый выбор стратегий по сущностям:**

| Сущность | Hinted Handoff | Read Repair | Anti-Entropy Repair | Обоснование |
|----------|---------------|-------------|--------------------|-|
| `carts` | ✅ Основная | Фоновый | Еженедельно | Высокая запись, низкие требования к консистентности, TTL очистит устаревшее |
| `guest_carts` | ✅ Основная | Не нужен | Не нужен | Живут 1 час, потеря некритична |
| `order_history` | ✅ Запасной | ✅ Основной | ✅ Обязательно | Нельзя терять заказы, читается часто |
| `user_sessions` | ✅ Основная | Фоновый | Не нужен | Короткий TTL, потеря сессии = повторный логин, некритично |

Компромисс между latency и консистентностью: для корзин и сессий выбираем `EVENTUAL CONSISTENCY` через Hinted Handoff — пользователь не заметит задержки в 100-200мс при синхронизации. Для истории заказов используем `QUORUM` чтение с Read Repair — чуть медленнее, зато данные всегда актуальны и ни один заказ не потеряется.
